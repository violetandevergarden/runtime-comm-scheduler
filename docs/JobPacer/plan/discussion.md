# JobPacer runtime 设计讨论总结

日期：2026-09-16。实施范围以 [Phase 3.1 计划](phase3.1.md) 为准，后续阶段的设计方向不等于本阶段必须实现的功能。

2026-09-28 补记：第 1–10 节保留初始设计上下文；第 11–15 节记录 GPU 实验后的性能、架构与研究讨论，不代表已决定改造协议或启动新实验。当前 GPU workload 合同以[统一 DAG 设计](phase3-gpu-workload-and-scheduling.md)和[七臂实验计划](phase3-gpu-seven-arm-experiments.md)为准。例如，新实验的 workload/tensor 样本身份与 epoch、repeat 分离，第 7 节包含 epoch 的历史采样方式不覆盖新合同。CPU/Gloo 历史数据用于机制分析，不作为真实 GPU compute 的配对性能基线。

## 1. 总体决定

新 runtime 独立设计和重写，不要求兼容或复用现有 Plan、scheduler、Work、executor、任务身份字段。先定义正确性、执行语义与实验要求，再实现代码。旧实现可作为历史实验对照，不进入新核心依赖链。

采用中心化 coordinator，依据运行状态决定 collective 准入；各 rank 保存真实执行对象，执行共同 grant。Policy 逐次产生顺序，coordinator 负责合法性检查、提交决定和有序发布，不提前替 policy 排完整序列。

Phase 3.1 聚焦线性 job、单竞争资源和严格串行通信。DAG、多进程部署和多链路调度分阶段展开，不提前建设完整通用框架。

## 2. 动态 runtime 的价值

静态 Plan 根据预估情况提前确定跨 job 顺序，队首未 ready 时可能阻塞其他已 ready 的任务。Runtime 利用实际到达、完成和 job 进度，减少预测错误导致的空闲，也能有界等待预计即将到达的重要任务。

例如 A 在 10 ms ready、B 在 2 ms ready，两项通信各耗时 3 ms，无跨 job 依赖且要求串行：静态 A→B 在 16 ms 全部完成；动态先 B 后 A 可在 13 ms 完成。

Runtime 也允许运行中注册任务，不要求启动前知道全集。但动态调度不保证更快：控制通信、状态汇聚、决策和主动等待均有成本；稳定 workload 的静态顺序可能很好。通信并发也可能优于串行，不能把动态选择收益与限制并发收益混淆。

## 3. 职责与任务模型

```text
Workload / framework adapter
    │ declare（可选） / submit
    ▼
Rank Runtime ─── OFFER / SUBMITTED / COMPLETED ───► Coordinator
    ▲                                                 │
    │                                       合法候选 → Policy
    └────────────────── GRANT ────────────────────────┘
    │
单 host launch worker → collective backend
```

| 对象或组件 | 职责 |
| --- | --- |
| TaskSpec | 跨 rank 一致的任务身份、group、collective 参数与约束 |
| TaskHint | 预计 ready、通信时长、remaining tail；与任务身份分开 |
| LocalBinding | 本地 tensor、ProcessGroup、producer event、执行入口 |
| Rank Runtime | 接收提交、保存绑定和 handle、处理 grant、独立探测完成与传播错误 |
| Coordinator | 成员状态、顺序和容量检查、提交并发布共同决定 |
| Policy | 从合法候选选择或有界等待，不接触线程、网络和 tensor |

submit 保存请求后立即返回 handle，不等待 grant。应用在消费位置等待；runtime 独立上报完成。建立 consumer stream 依赖与等待主机可观察的物理完成需分开定义。

## 4. ProcessGroup 内的顺序一致性

同一 collective 具有跨 rank 一致的任务身份、group 内序号及兼容参数。序号由 adapter 按共同语义产生，不能按本地线程到达顺序独立编号。Coordinator 校验成员信息，收齐所有成员 OFFER，仅让符合 group 顺序的任务进入候选。

选择一旦成为 grant，即追加到不可重排的共同序列。各 rank 接收自己参与的投影，由唯一 launch worker 按序调用底层 collective，不能交回 job 线程自由发射。

全局 decision_seq 标识决定；每 endpoint 连续的 delivery_seq 检查本地消息缺失，避免将不参与的全局任务误判为丢包。必须同时实现有序发布、单接收队列和单执行入口，只有序号或优先队列不够。

核心不变量：每个 rank 实际提交记录始终是其 grant 投影的前缀；同 group 所有成员因此执行同一序列的前缀。可以进度不同，不能交换、跳项或重复提交。受管理 group 的全部 collective 必须经过 runtime。

## 5. 多个 collective 在途与 policy 的能力

顺序一致不要求上一任务完成：rank 0 已提交 A、B，rank 1 才提交 A，仍可保持 A→B。顺序进度、提交进度、完成进度应分开。

但 host 次序一致不独立证明多 communicator 的设备并发安全。Backend 还需满足实际 PyTorch/NCCL/CUDA 配置的设备端排序要求，不能只取消完成屏障。参见 [NCCL 多 communicator 并发说明](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/communicators.html#using-multiple-nccl-communicators-concurrently)。

Grant 是不可撤销的决定提交点：某成员可能已经执行，其他成员不能撤回或插队。提前 grant 越多，policy 对新到达任务的反应空间越小。若启动时 grant 全部任务，就退化为静态顺序。

后续可分别限制 max_inflight（已 grant 未全局完成）和 max_unsubmitted（未收齐提交回执）。容量是上限，不要求 policy 填满；可以等待未来任务。Phase 3.1 只实现全局一个在途任务，不做撤销或第二套容量控制。

## 6. 候选与有界等待

eligible 是成员和依赖条件已满足的任务；anticipated frontier 是可能很快到达的前沿。线性 job 只考虑当前下一项，不能因远端后继 tail 很大而等待它、阻止其前驱获服务。

- Dynamic FIFO 按首次进入 eligible 的顺序选择，稳定 ID 仅破同分。
- Dynamic LTF 按 `estimated_comm_s + remaining_tail_s` 选择最长估计剩余路径，估计不读取真实未来扰动。
- Bounded lookahead 为目标建立固定截止时间；状态更新可提前重算，不能反复刷新预算。到期有候选就回退服务。

等待需比较预期收益和空闲成本；仅目标 tail 更大不够。第一版采用透明的简单启发式，并记录估计与实际结果，不追求全局最优。

## 7. 静态与动态效果比较

主要对照在新 runtime 内完成：StaticOrder 与动态策略共用协议、执行 backend、完成探测和日志。StaticOrder 输入任务 ID 序列，下一项未 eligible 就等待，不能跳过；完整序列不是其他策略的启动条件。

旧系统对新系统的整体对照另行进行，用于衡量迁移总效果，不能单独归因 policy 收益。

实验应保持 workload、成员、collective 参数、计算/消费位置和并发限制相同。Profiling 估计与实际扰动分离；首轮策略共享固定估计，在线更新估计另设实验。

按 (seed, epoch, job, task, rank) 固定计算扰动样本，不按线程次序取随机数；固定计算时长，而不强制固定请求绝对 ready 时间，因为调度改变后续推进属于真实反馈。

记录 job 完成时间、总体 makespan、eligible 等待、主动等待、grant 到提交和完成探测时间。区分无候选、静态队首阻塞、主动等待、容量满。中央接收时间与本地执行时间分开，不直接相减各 rank 原始时钟。

先无扰动与确定性错位，再多 seed 扰动。CPU/Gloo 验证机制；真实 GPU 实验才说明相应通信环境的性能，并保留 bare 并发基线。

## 8. Phase 3.2：DAG

DAG 改变合法候选：同 job 可以有多个独立前沿，不能永远用一个 job 队首表示。区分提交顺序约束与完成依赖，不能把所有边都解释为 host 等待物理完成。

DAG executor 位于 workload/framework 层，runtime 管通信准入，policy 可读关键路径等摘要，无需托管计算节点。DAG 独立不代表同 group 内可以由各 rank 自由重排；若未来支持，需中央共同分配执行顺序。

Phase 3.1 只实现线性推进，不做通用 DAG schema、环检测或计算执行器。

## 9. Phase 5：中心化管理与多进程执行

继续采用中心化 coordinator。Phase 3.1 可放在 rank 0 内，Phase 5 再独立部署。控制消息不携带 tensor、ProcessGroup、CUDA event 或 closure，不使用受调度 collective 作为控制 rendezvous。

每 GPU 一个 worker 适合托管式 replay。真实多个 job 进程共享 GPU 时，各进程执行端仍持有自己的 tensor 和 group；可增加 GPU controller 管理提交交接，不强制搬迁执行对象。

跨进程先发 A 许可再发 B 不能保证实际调用顺序。需要交接时，收到 A 实际 SUBMITTED 后才允许 B；不必等待 A 完成。跨 CUDA context 并发需单独验收。

Job Agent 可负责生命周期、注册、状态汇聚，不必每 job 强制新增进程。只有汇聚而非逐条转发才能减少中央成员级事件；中央逐 collective 决策仍有吞吐上限。先测事件速率、排队和 grant 延迟，再决定批处理或按竞争域下放。批量 grant 会提前锁定顺序，扩展吞吐与动态性存在取舍。

身份上分开 job、group、endpoint 与 GPU，不同 job 的 rank 0 不是同一个执行端。本阶段不做服务发现、恢复、sidecar 或独立 Job Agent。

## 10. Phase 6：多链路

多链路改变可同时执行的任务组合。后续用资源需求与占用替代单个在途计数；跨多资源任务由中央一次性检查、预留，避免部分占用后互相等待。

资源共享不必互斥。可以先采用不相交任务并行，再通过测量增加容量与干扰模型；真实路由需要拓扑/backend 信息，不能只凭成员集合推断。

等待链路 X 上的未来任务不应自动阻塞仅用 Y 的任务，后续需扩展等待作用范围。资源可并行与 backend 顺序安全分别校验。中央调度可以继续保留，分域不是必选项。

Phase 3.1 仅采用全局一个抽象竞争资源，不提前实现资源图、链路发现、多资源预留或任务集合优化。允许后续按需要修改 API。

## 11. Bare 的优势：带宽、执行空档与计算余量

### 11.1 已有证据与待验证解释

历史 CPU 场景中出现过 bare 快于旧静态 scheduler 和新 runtime 的结果，但不能概括为所有 workload 必然如此。首轮 GPU 批次没有完成可比的 bare 七臂验证；截至本补记，[七臂实施记录](../process/phase3-gpu-seven-arm-implementation-20260928.md)仍标明 bare 未通过资格验证，未启动 GPU profile、pilot 或正式矩阵。因此，“GPU bare 比所有策略快”尚不是验收事实。

用户提出三个解释：裸发可能更充分利用带宽；多个通信共享带宽可能利用独立计算尚未结束的时间；bare 没有调度系统的额外成本。它们值得验证，但需要区分以下机制：

| 候选机制 | 需要区分或观测的内容 |
| --- | --- |
| 并发提高链路利用率 | 单通信是否已经接近当前条件下的有效吞吐上限；并发是否提高总有效吞吐 |
| 提前排队减少空档 | 即使设备最终串行执行，bare 是否减少了上一通信完成到下一通信开始的间隔 |
| 利用通信时间余量 | 单通信变慢是否仍在结果被需要之前完成；是否提前解锁其他 job 的后继工作 |
| 避免静态队首阻塞 | 队首未 ready 时，是否存在其他可以合法执行的任务 |
| 减少控制与执行交接 | 请求、成员汇聚、grant、线程唤醒、完成反馈中有多少时间暴露在关键路径 |

带宽优势来自早期交接经验，目前应作为待复测假设。单通信耗时变长而应用 makespan 变短，并不能单独证明总带宽利用率提高。

### 11.2 Consumer 计算不决定通信容量释放

历史 H lane 的 consumer compute 是提交后、等待前的独立计算；它不是必须等通信完成才能开始的依赖消费者。通信已经完成而独立计算仍在继续，本身可以表示通信成功被隐藏。

代码上，旧 `AdmissionScheduler._poll_completions()` 独立探测完成并移除 inflight；新 coordinator 在全部成员 COMPLETED 后释放容量。两者均不要求应用 consumer 结束后才释放。因此，串行 scheduler 也可以在 A 通信完成、A 独立计算继续期间执行 B 通信。Bare 可能额外获得的机会，是在 A 通信尚未结束时就推进 B，或者减少相邻通信间的控制空档。

共享带宽不必然改善 makespan。理想化例子：A、B 同时 ready，各需独占链路 4 ms，A 同时有 10 ms 独立计算，B 没有独立计算；忽略启动成本和计算干扰，A→B 串行时 B 在 8 ms 结束、整体在 10 ms 结束；两通信平均共享带宽时均在 8 ms 完成，整体仍为 10 ms；若 B→A 串行，整体仍为 10 ms，但 B 可在 4 ms 结束。应同时检查 makespan、mean JCT 和逐 job JCT，而非把并发或单通信变慢本身解释为收益。

真实 GPU 计算与通信还可能竞争设备资源；CPU sleep 不体现这类干扰。新 GPU 实验需测实际计算时长变化、通信时长、设备空档与重叠，并用应用终点判断收益。详细 trace 单独诊断，不能把其扰动混入主性能比较。

## 12. 新 runtime 的固定闭环成本与收益门槛

### 12.1 当前能支持的结论

[CPU A–F 诊断](../result/phase3-runtime-overhead-20260924.md)显示，特定零计算通信链的新旧路径差距约为每 collective 2 ms 量级，policy 函数计算中位约 3 μs；控制消息、成员到齐、应用推进、线程交接和完成反馈共同占据路径，尚未完成互不重叠的精确因果分解。[首轮 GPU 固定链](../result/phase3-gpu-20260927.md)的额外时间约为每项 4.7–5.4 ms。这些都是对应批次的整条执行路径差异，不是通用常数，也不是已单独测出的纯中心化通信成本；最终统一 DAG 实现需要重新测量。

没有单个巨大热点并不意味着不可优化。严格单在途使“请求→成员到齐→决定→发射→完成探测→回报→下一决定”的小延迟反复累积。应优先区分设备仍在执行、完成尚未被探测、回报未到齐、下项尚未 ready、策略主动等待和线程交接，而不是优先优化已经很短的 policy 函数。

已有消融也说明局部改善不等于应用加速：减少独立 DECLARE 在 32 项零计算链中节省约 13–14 ms，但没有在 L0/L1 上稳定降低 makespan；提交时唤醒 completion thread 提前了首次 probe，也没有稳定缩短整体执行。这些历史观察不证明所有消息优化无效，但要求每项优化检查最终关键路径和 CPU 代价。

### 12.2 优化候选与约束

- 预注册稳定元数据，减少重复序列化、队列交接和不必要的热路径观测。
- 合并已经到达且不需额外等待的控制消息；不能为了凑批而任意延迟 OFFER 或 COMPLETED。
- 缩短物理完成至后续发射的空档，同时保持 SUBMITTED 先于 COMPLETED、全成员完成释放容量及有界失败退出。
- 批量 grant 会提前锁定顺序；当前 max_inflight=1 下不能直接把多个任务同时 grant 当作透明优化。
- 合并 tensor/collective 会改变 ready 时刻、通信粒度和重叠机会，属于另一类 workload/backend 优化，不能与控制消息批处理混为一谈。

### 12.3 策略需要抵消多少成本

对同一个配对样本，令 `T_o` 为旧 static 时间，`T_s` 为采用同一静态顺序的新 static 时间，`T_d` 为新 dynamic 时间，则：

```text
T_o - T_d = (T_s - T_d) - (T_s - T_o)
净收益     = 新 runtime 内动态改善 - 新旧静态路径差距
```

这是配对时间恒等式，不是独立的因果分解。先逐样本计算，再按实验合同汇总；不能把不同 arm 的汇总中位数任意相减当成配对结果。胜过新 static 不等于胜过旧 static 或 bare，必须分别报告。

一般 DAG 不能简单用“全部通信次数 × 2 ms”预测损失；关键是额外等待有多少暴露在应用关键路径上。更可能获得净收益的场景包括反复队首失配、不同后继计算长度、实际 ready 波动，以及多个有意义的候选选择。稳定单链且没有值得等待的未来候选时，动态策略可利用的空间很小。分析候选数时也须包含有界等待可能带来的选择，不能只统计同一瞬间 ready 的数量。

## 13. 合成 DAG 的代表性与真实训练接入

手工 DAG 可以验证协议正确性、机制是否触发、策略怎样改变顺序，以及不同计算/通信比例下的收益边界。其局限是不能单独证明这些结构和扰动在真实训练中的频率，也不能证明提前通信不会拖慢真实计算。增加 seed 与 repeat 能增强样本内结论，不能替代对目标负载的代表性检查。

“Megatron 每次通信很大，所以几毫秒可以忽略”应作为假设而非前提。Megatron DDP 支持梯度分 bucket 后异步 all-reduce/reduce-scatter，并支持参数 all-gather 与计算重叠；TP 也有通信与 GEMM 分块重叠机制。大模型不等于所有通信单元都大，完整节点物理完成推进也不等同于框架内部流水粒度。参见 [Megatron DDP 文档](https://docs.nvidia.com/megatron-core/developer-guide/latest/apidocs/core/core.distributed.distributed_data_parallel.html)与[并行配置文档](https://docs.nvidia.com/megatron-core/developer-guide/latest/apidocs/core/core.model_parallel_config.html)；实际接入需固定版本和配置。

例如，通信原需 20 ms、可被计算隐藏 19 ms，若新增 2 ms 准入等待且计算窗口不变，暴露时间可能由 1 ms 增至 3 ms；若窗口足够长，新增等待也可能完全被隐藏。因此应测通信结果何时被需要，而非仅比较控制成本与通信总时长。

需要区分两个研究对象：多个训练 job 共享资源时的通信调度，主要看 job 进度、JCT、吞吐与公平性；单个训练 job 内部 DP/TP/PP 等通信调度，主要看依赖、合法重排空间和 step time。当前多 job/group 手工图不能自动代表后者。现阶段核心只支持 all-reduce，也不能声称已经覆盖 distributed optimizer 等使用其他 collective 的配置。

建议尽早采集一个明确训练配置的 trace，无需先完成整个 Megatron 接入。记录通信类型、大小、ready 和结果使用时刻、计算干扰、候选并存程度、迭代稳定性，据此修正合成 DAG；随后选择范围明确的接入点，例如 DP 梯度通信。只把实际测得的规模与机制写成结论。

## 14. 中心化、去中心化与减少决策频率

### 14.1 当前判断

用户提出去中心化设计困难，但可能存在更低成本的特殊设计。当前判断是：在本项目的双 rank、单全局资源、严格单在途合同下，去中心化的设计和验证成本预计更高，运行成本未必更低。现有证据更支持逐项闭环延迟问题，尚未证明中央节点因请求量过大而吞吐饱和。不能把当前毫秒级执行差距全部视为中心化架构不可避免的代价。

| 方面 | 中心化 | 去中心化 |
| --- | --- | --- |
| 共同决定 | 单点决定并有序发布 | 需共同状态、决策权限或预先约定的顺序 |
| 热路径成本 | 状态汇聚、下发及执行反馈 | 可能减少跳数，也可能增加状态交换轮次 |
| 扩展性 | 汇聚和处理可能形成瓶颈 | 可分散负载，但总消息量可能增加 |
| 故障处理 | 中央失效后统一停止较明确 | 部分失联、状态分歧和权限交接更复杂 |
| 调试与验证 | 重建一条共同决定序列 | 需重建跨节点因果关系 |

去中心化不自动带来容错。若仍采用任一关键成员失败就终止 epoch 的模型，分散决定并不等于实现了故障恢复；也不必因此引入通用共识或选主框架。

### 14.2 无法仅靠相同算法消除的信息需求

若 rank 0 只看到 A ready，rank 1 只看到 B ready，即使运行相同 FIFO/LTF，也可能选出不同任务。稳定 ID 只能解决相同候选集合中的同分，不能解决候选集合不同。必须交换足够状态、指定决定者，或预先约定顺序并等待；把排序交给其他机制也需要验证其实际语义。

当前容量要求全部成员物理完成后释放。提前知道下一项任务，不等于已经知道上一项全局完成。去掉 coordinator 并不会消除这种信息需求。相同 host 发射顺序也不足以证明多 communicator 的设备并发安全。

### 14.3 候选方向一：稳定区间复用计划，关键边界集中决定

预注册 DAG、身份和估计，在稳定区间复用共同顺序，在计划失配或有意义的竞争边界重新决定，只修改尚未提交的后缀。研究对象是哪些决定值得在线做、哪些可以复用，以及复用长度与策略损失之间的关系。

本地发现异常后不能自行切换顺序，需在共同边界一致切换计划版本。该方案首先减少排序、元数据处理和决定发布；保留当前严格容量语义时，逐项全局完成门控仍然存在，不能宣称缓存顺序已消除整个闭环。当前倾向优先研究此方向，但尚未决定实施。

### 14.4 候选方向二：按区间授予执行权限或传递令牌

中央可以研究向一个 job 授予一段执行权限，由其成员按共同顺序推进，从而把跨 job 协调成本摊到多个任务。代价是紧急任务响应变慢、权限持有者未 ready 时可能空闲，以及交接必须处理尚未完成的通信，不能仅靠本地超时认定权限安全释放。

若每项仍传一次令牌并收齐全成员完成确认，未必比中央决定更快。若保留全局单在途，权限内部仍需保证逐项容量语义；允许连续预发则属于合同修改。研究价值在于协调粒度与调度响应性的权衡，不在于令牌本身天然低开销。

### 14.5 候选方向三：按真实资源冲突范围分域

当未来任务使用独立瓶颈时，可只让真正竞争同一资源的任务协调。当前所有任务共享一个抽象容量，按 group 拆 scheduler 不自动得到资源独立性；必须先证明资源可分或明确修改资源模型。该方向属于后续多资源研究，不用它解释当前双卡固定闭环差距。

“各 rank 按同一优先级直接发”也不是无条件的捷径：等待未 ready 的高优先级项可能退化为静态队首阻塞，各自跳过又可能产生顺序分歧，交换 ready 信息则重新引入协调。通信排序已有相关研究，例如 [TicTac](https://proceedings.mlsys.org/paper_files/paper/2019/file/94cb28874a503f34b3c4a41bddcea2bd-Paper.pdf)，但不能据其排序收益推断本项目的独立本地决策安全或高效。

## 15. 后续研究的判定顺序

1. **完成统一 GPU 路径的小规模语义与性能验证。** 按七臂计划使用共同输入、估计和执行语义；bare 不合格时明确缺项，不以 raw-ordered 偷换。除总体时间外检查通信空档、实际计算干扰、队首阻塞、候选与等待情况、逐 job JCT。此处不追加大型矩阵。
2. **定位收益边界。** 在少量代表 DAG 上改变通信粒度、独立计算长度和 ready 偏斜，比较闭环成本、可隐藏余量和可避免的关键路径等待。小图可离线枚举合法顺序，估计给定模型下的收益空间；这不是在线策略可以读取真实未来扰动的授权，也不是对真实 GPU 的无条件性能上界。
3. **分离决定顺序与完成门控的成本。** 研究预先给定顺序、保持相同物理完成和容量语义时的执行成本；测量有多少决策实际值得改变。若增设消融执行路径，应明确它改变了哪些步骤，不能只把旧 scheduler 当成完全匹配的最低成本实现。
4. **尽早用真实训练 trace 校准问题。** 先确定是跨 job 还是单 job 内部调度，再检查合成输入的代表性，选择明确的框架接入范围。
5. **依据结果选择架构投入。** 稳定区间多、少数边界需调整时，优先考虑计划复用和稀疏动态决定；每一步均依赖最新跨 rank 状态时，先优化中央热路径；只有出现明确中央吞吐瓶颈或真实资源可分，才进一步评估全面去中心化或分域。

讨论结论不是承诺新 runtime 必然获益，也不是决定重写去中心化系统。下一阶段要回答的是：净收益存在于哪些负载、需要多细的调度粒度、哪些全局信息不必反复获取，以及省下协调后会损失多少动态性。当前代码、七臂实验合同和 Phase 5 中心化方向不因本补记自动改变。
